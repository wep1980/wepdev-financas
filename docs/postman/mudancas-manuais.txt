MUDANÇAS MANUAIS NO POSTMAN — account-service, transaction-service e card-service
==================================================================================

Este arquivo existe porque a collection do Postman NÃO é reimportada a
cada mudança de contrato (o usuário já personalizou a collection importada
e não quer perder isso). Toda vez que um endpoint mudar, atualize a
collection manualmente seguindo as instruções abaixo E atualize este
arquivo na mesma sessão — não deixar acumular mudança sem registrar.

Fonte de verdade do contrato: docs/specs/account-service.yaml,
docs/specs/transaction-service.yaml e docs/specs/card-service.yaml
(spec-driven). Este arquivo é só um guia de "o que mexer na collection à mão".


------------------------------------------------------------
1. VARIÁVEIS DE ENVIRONMENT (confira se já existem)
------------------------------------------------------------

Variável                          | Valor                  | Tipo
-----------------------------------|-------------------------|--------
keycloak_service_client_id        | transaction-service     | default
keycloak_service_client_secret    | changeit                | secret

Necessário só se for testar os endpoints internos (/debitos, /creditos)
com role "service" antes do transaction-service existir de verdade.

2026-08-07 — CRUD completo + usuarioId do token (não mais do cliente)
------------------------------------------------------------

MUDANÇA DE CONTRATO (breaking change) em requests que já existiam:

POST /api/v1/contas
  - Remover "usuarioId" do body. O dono da conta agora é sempre extraído
    do token (claim sub), nunca enviado pelo cliente.
  - Body novo:
    {
      "nome": "Conta corrente",
      "tipo": "CORRENTE",
      "saldoInicial": 100.00,
      "instituicao": "Banco X"
    }
  - Se "usuarioId" for enviado mesmo assim, é ignorado (não existe mais
    no schema, não dá erro).

GET /api/v1/contas
  - Remover o query param "usuarioId". URL passa a ser só
    {{baseUrl}}/api/v1/contas (sem parâmetro) — lista as contas do
    usuário do token automaticamente.

GET /api/v1/contas/{id}
  - Sem mudança de request. Mudou o comportamento: conta de outro
    usuário agora responde 404 (antes não tinha essa checagem).

REQUESTS NOVOS PRA CRIAR NA COLLECTION:

PUT /api/v1/contas/{id} — atualizar conta
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Header: Content-Type: application/json
  - Body (raw JSON):
    {
      "nome": "Nome novo",
      "instituicao": "Banco Y"
    }
  - Respostas: 200 (atualizado) / 400 (nome ausente/vazio) /
    404 (não existe ou não é sua)

DELETE /api/v1/contas/{id} — excluir (lógico) conta
  - Auth: OAuth 2.0, mesmo token de usuário
  - Sem body
  - Respostas: 204 (sucesso, sem corpo) / 404 (não existe ou não é sua)

FORMATO DE ERRO MUDOU (útil se tiver test scripts com pm.test checando
corpo de erro):

  404 / 422 (conta não encontrada, saldo insuficiente):
    { "mensagem": "Conta não encontrada: <id>" }

  400 (validação de campo, ex: nome ausente):
    {
      "mensagem": "Erro de validação",
      "erros": [
        { "campo": "nome", "mensagem": "não deve estar em branco" }
      ]
    }

Se havia test script checando status/corpo dos erros antigos, ajustar pra
essa estrutura.

2026-08-07 — transaction-service: registrar transação (endpoint novo)
------------------------------------------------------------

Serviço novo, porta 8082. Se ainda não tem uma collection pra ele, importe
de http://localhost:8082/q/openapi (com o serviço rodando) — é a primeira
vez, então reimportar não perde nada (ver seção 2 do README principal do
Postman). Depois disso, siga este arquivo pra mudanças futuras, mesmo
esquema do account-service.

POST /api/v1/transacoes — registrar transação
  - Auth: OAuth 2.0, token de usuário (role "usuario") — mesmo token
    usado no account-service, mesmo usuário.
  - Header: Content-Type: application/json
  - Body (raw JSON):
    {
      "contaId": "<uuid de uma conta sua, já criada no account-service>",
      "descricao": "Mercado",
      "valor": 120.00,
      "tipo": "DESPESA",
      "categoria": "Alimentação",
      "dataTransacao": "2026-08-07"
    }
    (tipo: RECEITA ou DESPESA; categoria e dataTransacao são opcionais —
    dataTransacao omitida usa a data de hoje)
  - Respostas: 201 (criada, status vem sempre CONFIRMADA) /
    400 (campo obrigatório ausente) /
    404 (contaId não existe ou não é sua) /
    422 (saldo insuficiente, só pra DESPESA)
  - Importante: o account-service precisa estar rodando também — este
    endpoint chama ele de forma síncrona antes de salvar a transação.

GET /api/v1/transacoes — listar transações
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Sem body. Query params opcionais:
    contaId=<uuid>   (filtra por conta)
    inicio=2026-08-01   (data, formato AAAA-MM-DD)
    fim=2026-08-31
  - Resposta: 200, lista de transações do usuário autenticado, mais
    recente primeiro. Sem os params, traz tudo do usuário.

2026-08-07 — transaction-service: cancelar transação (endpoint novo)
------------------------------------------------------------

DELETE /api/v1/transacoes/{id} — cancelar transação
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Sem body. {id} é o "id" que veio na resposta do POST /transacoes.
  - Reverte o efeito no saldo (síncrono com account-service): cancelar uma
    DESPESA credita de volta, cancelar uma RECEITA debita de volta.
  - Respostas: 204 (cancelada, sem corpo) /
    404 (não existe ou não é sua) /
    422 (não deu pra reverter — ex: cancelar uma RECEITA cujo dinheiro já
    foi gasto em outro lugar, a conta não tem mais saldo suficiente)
  - Idempotente: chamar de novo numa transação já cancelada continua 204,
    sem reverter o saldo outra vez.
  - Importante: o account-service precisa estar rodando também, mesmo
    motivo do POST.

2026-08-08 — transaction-service: editar transação (endpoint novo)
------------------------------------------------------------

PUT /api/v1/transacoes/{id} — editar transação
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Header: Content-Type: application/json
  - {id} é o "id" que veio na resposta do POST /transacoes.
  - Body (raw JSON):
    {
      "descricao": "Mercado maior",
      "valor": 150.00,
      "categoria": "Alimentação",
      "dataTransacao": "2026-08-08"
    }
    (descricao e valor são obrigatórios; categoria e dataTransacao
    opcionais — dataTransacao omitida mantém a data já gravada)
  - contaId e tipo NÃO são editáveis por este endpoint — pra trocar de
    conta ou tipo, cancele a transação e crie outra (evita ambiguidade de
    reversão de saldo entre contas diferentes).
  - Se o valor mudou, ajusta o saldo pela DIFERENÇA (delta) numa chamada
    só ao account-service — não reverte-e-reaplica em duas chamadas.
  - Respostas: 200 (atualizada, corpo com a transação) /
    400 (descricao ou valor ausente/inválido) /
    404 (não existe ou não é sua) /
    422 (transação já cancelada — não pode ser editada; ou saldo
    insuficiente após ajustar a diferença de valor)
  - Importante: o account-service precisa estar rodando também, mesmo
    motivo do POST/DELETE.

2026-08-08 — transaction-service: resumo por categoria (endpoint novo)
------------------------------------------------------------

GET /api/v1/transacoes/resumo-por-categoria — resumo de gastos por categoria
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Sem body. Query params obrigatórios:
    inicio=2026-08-01   (data, formato AAAA-MM-DD)
    fim=2026-08-31
  - Só soma DESPESA com status CONFIRMADA — RECEITA e transação CANCELADA
    não entram. Transação sem categoria agrupa em "Sem categoria".
  - Resposta: 200, lista ordenada por totalGasto decrescente (empate
    desempatado por nome da categoria), cada item com:
    {
      "categoria": "Alimentação",
      "totalGasto": 150.00,
      "percentualDoTotal": 75.00,
      "totalGastoPeriodoAnterior": null
    }
    totalGastoPeriodoAnterior compara com o período imediatamente anterior
    de mesma duração em dias; vem null se a categoria não teve gasto nele.
  - Respostas: 200 / 400 (inicio ou fim ausente, ou inicio depois do fim).
  - Não depende do account-service (só lê o que já está no banco do
    transaction-service).

2026-08-08 — transaction-service: transações recorrentes (recurso novo)
------------------------------------------------------------

POST /api/v1/transacoes-recorrentes — criar regra recorrente
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Header: Content-Type: application/json
  - Body (raw JSON):
    {
      "contaId": "<uuid de uma conta sua>",
      "descricao": "Salário",
      "valor": 5000.00,
      "tipo": "RECEITA",
      "categoria": "Salário",
      "frequencia": "MENSAL",
      "dataInicio": "2026-08-08",
      "quantidadeOcorrencias": null
    }
    (contaId/descricao/valor/tipo/frequencia/dataInicio obrigatórios;
    categoria opcional; quantidadeOcorrencias omitido/null = indefinida,
    repete até cancelar — ex. salário. Um número fixo, ex. 24, faz a
    regra virar CONCLUIDA sozinha depois da última ocorrência)
  - Gera a 1ª ocorrência (uma Transacao normal, com transacaoRecorrenteId
    preenchido) IMEDIATAMENTE, síncrono com o account-service — mesmo
    efeito no saldo de um POST /transacoes comum.
  - Respostas: 201 (regra criada, corpo já reflete ocorrenciasGeradas=1) /
    400 (campo obrigatório ausente) /
    404 (contaId não existe ou não é sua) /
    422 (saldo insuficiente na 1ª ocorrência, só pra DESPESA)
  - Importante: o account-service precisa estar rodando também, mesmo
    motivo do POST /transacoes.

GET /api/v1/transacoes-recorrentes — listar regras
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Sem body. Query param opcional: status=ATIVA (ou PAUSADA/CANCELADA/CONCLUIDA)
  - Resposta: 200, lista de regras do usuário autenticado.

GET /api/v1/transacoes-recorrentes/{id} — buscar regra
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Respostas: 200 / 404 (não existe ou não é sua).

DELETE /api/v1/transacoes-recorrentes/{id} — cancelar regra
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Sem body. Exclusão lógica — NÃO afeta transações já geradas por essa
    regra (elas continuam existindo, editáveis/canceláveis normalmente via
    /transacoes/{id}). Idempotente.
  - Respostas: 204 / 404 (não existe ou não é sua).

GET /api/v1/transacoes-recorrentes/proximos-vencimentos — [endpoint interno]
  - Auth: OAuth 2.0, token de SERVIÇO (client_credentials, role "service")
    — mesmo client usado pra testar /contas/{id}/debitos|creditos no
    account-service, ver seção 1 deste arquivo e docs/postman/README.md.
  - Sem body. Query param obrigatório: dias=7 (janela de antecedência)
  - Resposta: 200, lista de próximas ocorrências de TODAS as regras ATIVA
    de TODOS os usuários dentro da janela — não filtra por usuário porque
    é consumido pelo futuro notification-service (ADR-0010), que resolve
    preferência por usuário separadamente.
  - Não é pra testar com token de usuário normal — dá 403 de propósito.

Job agendado: GerarOcorrenciasRecorrentesJob roda sozinho (cron diário,
não é um endpoint) e gera a próxima ocorrência de cada regra ATIVA
vencida — nada a testar manualmente no Postman aqui.

2026-08-09 — card-service: CRUD de cartão (serviço novo)
------------------------------------------------------------

Serviço novo, porta 8083. Se ainda não tem uma collection pra ele, importe
de http://localhost:8083/q/openapi (com o serviço rodando) — é a primeira
vez, então reimportar não perde nada (ver seção 2 do README principal do
Postman). Depois disso, siga este arquivo pra mudanças futuras, mesmo
esquema dos outros dois serviços.

Variável de environment nova (mesmo padrão de transaction_service_url):
card_service_url = http://localhost:8083

POST /api/v1/cartoes — criar cartão
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Header: Content-Type: application/json
  - Body (raw JSON):
    {
      "apelido": "Nubank Roxinho",
      "bandeira": "MASTERCARD",
      "limite": 5000.00,
      "diaFechamento": 5,
      "diaVencimento": 12,
      "contaPagamentoId": "<uuid de uma conta sua no account-service, CORRENTE/POUPANCA/CARTEIRA>"
    }
    (apelido/limite/diaFechamento/diaVencimento/contaPagamentoId
    obrigatórios; bandeira opcional, enum VISA/MASTERCARD/ELO/AMEX/OUTRA)
  - contaPagamentoId é confirmado contra o account-service antes de criar
    (mesma lógica de "conta precisa existir e ser sua" do transaction-service).
  - Respostas: 201 (criado) / 400 (campo obrigatório ausente) /
    404 (contaPagamentoId não existe ou não é sua).
  - Importante: o account-service precisa estar rodando também.

GET /api/v1/cartoes — listar cartões
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Sem body, sem query params. Resposta: 200, só cartões ativos do usuário.

GET /api/v1/cartoes/{id} — buscar cartão
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Respostas: 200 (mesmo se inativo — só não aparece na listagem) /
    404 (não existe ou não é seu).

PUT /api/v1/cartoes/{id} — atualizar cartão
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Mesmo body do POST (todos os campos obrigatórios de novo, exceto
    bandeira). contaPagamentoId é reconfirmado contra o account-service
    (pode ter mudado pra uma conta que não é sua).
  - Respostas: 200 / 400 / 404 (cartão ou contaPagamentoId).

DELETE /api/v1/cartoes/{id} — excluir cartão
  - Auth: OAuth 2.0, token de usuário (role "usuario")
  - Sem body. Exclusão lógica (ativo=false) — NÃO afeta faturas/compras já
    existentes (quando esse domínio existir). Idempotente.
  - Respostas: 204 / 404 (não existe ou não é seu).
